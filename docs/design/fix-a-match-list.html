Tell the project about this

If the program should have found this by itself, a report helps it learn the pattern. The program sends nothing: you copy the text, look it over, and post it on GitHub yourself.

Folders, players' addresses and sign-ins are left out. You can edit the text before posting.

What this shows

The "Fix a match" card on Titles & art once the two text boxes are gone: one row per fix, a cover, the read title, and what it was fixed to.

  • The row's name is the read title (what the fix is keyed on) or, for a fix for one file, the exact file name. The line under it says what happens: a pinned entry, "Searched as ..." (an old "Search under another name" line), "Your image" (an old "Pin a cover image" line), "Only this file", and "episodes +12" when an offset is set.
  • Old config lines show up as rows by themselves: the program turns them into fixes once, the first time a version with this list starts and the new setting is still empty (the design's migration section).
  • Edit opens the same Fix this match dialog, prefilled. Remove removes the row at once (settings save as they change); the bar under the window offers Undo for a few seconds, as other removals do.
  • Add a fix opens the dialog with an empty "read as" box, for a title that is not playing now.
  • Empty list: one sentence pointing to where fixes start (toggle it above).

Tell the project about this

  • The same pattern as Copy diagnostics: the text is shown, copied, and the GitHub issue form opens. No file name in the web address, nothing posted by the program.
  • The report holds the file name (never folders), what it was read as, the automatic match and the fix: exactly what a test case for the name reader needs. It is opt-in: it appears only when the user chooses it, and the program sends nothing itself.
